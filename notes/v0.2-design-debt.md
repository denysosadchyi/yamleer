# Design Debt — v0.2 Audit List

Items deliberately deferred from MVP. Each entry: current state, why
deferred, and the trigger that should prompt revisit.

---

## Secondary text via `opacity`, not `--color-text-secondary`

**Current state.** In `system/styles/blocks.css`, secondary text
(`[data-field="description"]`, `[data-field="lead"]`, `[data-field="body"]`)
uses `opacity: 0.8`–`0.85` rather than a dedicated colour token.

**Why deferred.** Opacity is **tone-aware** through the CSS cascade:
on `[data-tone="emphasis"]` the text colour is `--color-text-inverse`
(light) and `opacity: 0.85` of light text remains readable; on
`[data-tone="neutral"]` it dims `--color-text-primary` (dark) the same
way. Using `var(--color-text-secondary)` (a single palette value) would
render correctly only on light surfaces — on `tone:emphasis` it would
be unreadable.

The proper fix is per-tone secondary text in `design/tokens/roles.yaml`:

```yaml
tone:
  neutral:
    text: { token: text-primary }
    text-secondary: { token: text-secondary }   # exists
  emphasis:
    text: { token: text-inverse }
    text-secondary: { token: ??? }              # no palette mate yet
```

The blocker: there is no palette token for a "dimmed light grey on dark
surface" — `text-inverse-secondary` would need to be introduced. That
deserves a brand decision (which lightness, which chroma to dim), not a
guess.

**Revisit when ANY of:**
- WCAG contrast audit flags edge cases at any block × tone combination
- Dark mode is introduced (opacity often misbehaves on inverted UI)
- More than 3 tones become actively used (current active: neutral,
  emphasis, muted; danger and success defined but unused)
- Brand palette is finalised — a `text-inverse-secondary` mate would
  fall out of that work for free

## WCAG contrast audit for `[data-primitive="action"][data-intent="primary"]`

**Current state.** Action-primary background is `var(--role-primary)`
which resolves to `var(--color-brand-primary)` = `oklch(52% 0.16 250)`
(approx `#4a6fc7`). Text is `var(--color-text-inverse)` (white-ish).

Estimated contrast ratio: **~4.5:1** — at WCAG AA minimum for normal
text, **borderline**. Fails AAA. Could fail AA if the action label drops
below 14 px.

**Why deferred.** `--color-brand-*` is placeholder palette during MVP.
Finalising real brand colour will trigger a full WCAG sweep across the
button/link surfaces. Iterating contrast on placeholder colour is wasted
work.

**Mitigation if MVP ships with current palette.** Action labels render
inside a block context, inheriting `--type-body-size` (≥ 15 px at the
narrow viewport end), so they pass the small-text threshold. Confirm
this holds in Etap 4 storyboard.

**Revisit when ANY of:**
- Brand palette is finalised for the real project (post-Harbor sample)
- Etap 4 step 8 visual review reveals contrast issues on screen
- `--role-primary` starts being used as background in a non-button
  context (where text size may differ from button label)
- An accessibility-oriented user/agent reviews the system

## `ctx.escape` coverage lint

**Current state.** Renderers in `system/blocks/index.js` and
`system/primitives/index.js` rely on author discipline for XSS-safe
interpolation. There is no automated check that every `${data.<field>}`
in a renderer goes through `ctx.escape` (or the directly-imported
`escape`).

**Why deferred.** Day-2 task; the surface is small enough during MVP
that manual review catches drift. A regex or AST scan of the renderer
files for `\${data\.\w+}` without `ctx.escape\(` around it would close
the gap in ~30 lines.

**Revisit when:**
- A third renderer file is added (template renderers in
  `system/templates/index.js` will be next — already a candidate)
- Any escape-related bug is found in PR review
- Day-2 polishing pass begins

## `aria-labelledby` plumbing for primitives inside blocks

**Current state.** With the controls category landed in v0.1.1, blocks
that host a control primitive (today only `setting-row`) duplicate
the label string: `setting-row.label` for visible text + the inner
`toggle.aria-label` for the accessible name. Both fields are required;
the author writes the same string twice.

**Why deferred.** Only one block currently has the pattern
(setting-row → toggle). The cleaner fix — `aria-labelledby` plumbing
where the block renderer emits a stable `id` on `[data-field="label"]`
and the primitive renderer reads that id from render-context — needs
id-generation in the render context and an opt-in field on the
primitive (e.g., `labelled-by: <field-name>`). Premature for one
consumer.

**Mitigation today.** Author discipline: same string in both places.
The duplication is local (one block, one primitive), so drift risk
is low.

**Revisit when ANY of:**
- 3+ blocks declare a control field (setting-row, future
  `task-item`, future `form-field`/`form-row`, etc.) — the
  duplication starts showing up at scale
- A user-facing accessibility audit flags the duplication as
  confusing or as a maintenance hazard
- A new primitive is introduced where the natural label lives on the
  parent block (e.g., a `select` primitive where options are the
  point and a separate aria-label adds noise)
